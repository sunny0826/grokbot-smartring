## 已核对的入口

`Worker.process_one()` 保存 `jobs.ready`，`Mailbox` 通过原网关提供
`voice.claim/read/reply`。`claim_request()` 原子领取，`reply_request()` 保存不可变回复。
原网关事件只进入缓存，MCP 工具主动读取；这里没有启动 Bot 的调用。

[Grok Bot routine 官方说明](https://cursor.com/help/grok-bot/routines)明确支持
绑定原 Bot 的 webhook：POST JSON，`Authorization: Bearer <key>`，200 表示
接受并启动，不能当作回复完成。运行内部限流失败不会自动重试。
这与 [Grok automation 文档](https://docs.x.ai/grok/automations/webhooks)的
HMAC/202 是不同接口，不能混用。

通过 Grok Bot 桌面实际界面确认目标为「毛线」。用户确认授权后，已发送设置指令；
Bot 返回创建成功，详情列表可见「圆屏语音自动回复」，Webhook 触发且已启用。
Lody 当前工具管理 Lody 会话，不提供原 Grok Bot 的触发 API。

## 结构比较

两个同宿主默认模型的独立只读候选已完成，不是跨模型评审。
A 使用独立 notifications 表；B 在 jobs 保存通知进度。
共同约束：通知只携带请求 ID；网络发送在数据库锁外；200 后仍等待领取；
超时不声称失败；新运行生成新 claim_id，原运行重试保留其 claim_id；
已 claimed 永不自动重新执行。

第三个独立只读评判选择 B，主会话核对后采纳：每条请求只有一个唤醒目标，
用 jobs 的通知列足够，不增加第二套任务归属。吸收 A 的脱敏错误记录，
通知错误不覆盖业务 error。只有 ready 可通知，因此无需同步额外 done 状态。
采用幂等恢复原则：ready 与通知资格同事务，发送前持久化宽限期，
重复通知由不同运行的原子领取拦截。采用真实验证原则：200 不当作 Bot 回复证据。

三个独立会话均继承宿主默认模型。候选无产品写权；实施、配置及验收由主会话负责。

实现后独立审查发现领取回执丢失续接文案、自定义信箱 ID、全局限流及鉴权暂停恢复问题。
主会话均采纳：任务进度明确 not_started/started；指令按 mailbox-id 生成；
单行 activation_control 仅保存整个发送器的暂停和冷却（不另存任务队列），跨重启生效。
私密配置无终端时拒绝输入，避免 getpass 回退回显。新增注释审查无删除项；
发送前宽限期注释解释崩溃窗口，保留。
