# 独立裁决：以候选 B 为基础，吸收 A 的稳定定位与首屏预取

已完整读取两份候选；本轮只写本裁决文件，未修改产品、调用业务服务或操作 UI。定向 Nowledge 搜索确认既有目标是保留原毛线的自动收取与回复；历史“一分钟”只是合成 WAV 验证，不能替代本次阶段证据。以下运行数据来自协调者，未由本裁决重复采集。

## 选择及理由

**选择 B 作为基础，优势较小但明确。** 两份候选的核心结论一致：保持原 Bot 的记忆/工具，优先减少其实际发生的机械工具回合，避免先换 ASR。B 对测量边界、调用者契约、失败样本和故障回归的组织更完整（B:42–52、93–105），明确提醒删除两个工具不等于消除两者之间全部空档（B:38）。这比按工具数量直接推算收益更可靠。

## 两个嫁接点

1. **从 A:20、81 吸收“稳定设备定位与失效恢复”作为减少发现步骤的前提。** 先验证 mailbox 标识是否稳定、重连是否更换设备实例 ID；已有确定目标且 direct claim 契约支持时才跳过每次 list/get_state，失效时重新发现。不能把“已知 mailbox_id”当作永久可用的实例 ID，也不能用最新 state 替代当前 command 的回执。此项直接服务于当前主要延迟区间，优先于本地小优化。
2. **从 A:31、88 吸收“先预取首屏”并把它与连接复用拆开。** B:69 把连接复用排在设备尾延迟改造前面，但需要同步改服务端、线程槽、超时和认证行为，复杂度明显更高。首屏预取可以先独立评估：只在 replied 后缓存，显式查看才标已读；测量“点击→显示”，不宣称改善 Bot 处理时间。连接复用/长轮询待真实网络阶段数据后另决策。

## 必须修正的事实与优先级

- **HTTP 200：** 协调者已核对官方例行任务文档，200 表示请求已接受且已启动 run，不能沿用 B:16 的“不等于例行任务已启动”。仍不表示第一轮模型/工具已开始，更不表示业务完成。最终稿应引用该官方文档，并分别记录 HTTP 接受、首工具和 claim 完成，不把 200 当作最终回复成功。
- **时间戳：** 协调者确认网关 finish 日志位于执行等待之后，因此 A:16 / B:34 的“可能不是完成时刻”疑问可以移除。预留→claim/reply 的 22.022/40.336 秒和 18.151/30.380 秒仍是通知预留起算；不是云端接受起算，也不是结束录音起算。claim 完成→reply 完成分别为 18.314 秒、12.229 秒。这两条只足以定位重点区间，不足以计算稳定 p95 或精确拆分平台/模型/工具占比。
- **渲染：** 新补充本地测量为缓存渲染中位 0.0118 秒，范围 0.0115–0.0133 秒，初始化约 0.077 秒。结合网关 reply 的 0.316–0.379 秒量级，它不支持把本地渲染当作当前几十秒等待的主因。锁外渲染、像素批量化降为有并发阻塞证据时再做；保留设计说明即可。此结论只覆盖已测页面/运行条件。
- **P1 排序：** B:54 标题和 B:105 总顺序优于 B:56–58 的列表顺序。最终方案先呈现 Bot 真实回合核查与精简，再列服务预热、元数据窄查询。预热收益只属于冷启动；暖态 0.876 秒转写不值得作为本轮主线。

## 建议交付顺序与停止条件

1. **补齐最小阶段证据。** 利用现有日志加通知 HTTP 接受/结果时间、Bot 原生执行 trace、设备停止/上传/观察到回复/首屏显示时间；不新增模型日志工具回合，不先建监控平台。以普通问答、需原工具、需原记忆三类建立同类对照，区分冷/热、单条/连续、LAN/远程。暂时不可观测的阶段保留黑盒名称。
2. **单独验证减少机械回合。** 在稳定定位和 command 契约允许时直接 claim，避免无条件 list/get_state/read/status；纯问答不增加外部动作检查点。维持动作前持久化和未知结果核对。衡量工具调用数、对应阶段和端到端时延同时是否下降；没有稳定改善则不继续堆提示词补丁。
3. **独立做首屏预取试验；本地改善按证据排序。** 预取测点击到显示；预热测冷启动；窄列读取测查询成本。连续请求实证命中 15 秒门限时才分离首次通知与不确定重试限流。不能把这些小项合并后声称消除了 Bot 阶段等待。
4. **仅在前述结果证明必要时改变结构。** 流式上传/ASR只在长录音上传或转写占比大时考虑；同 Bot 确定性适配器必须先证实官方运行接口、持久状态、回调/重试契约；另模型快路由仍是另一个产品决定。

每一阶段只改一个关键因素，保留失败/重试样本；报告样本数、阶段中位数/可支持的尾部统计、成功率和关键语义准确率。沿用 B:103 的上传冲突、claim 竞争、回执丢失、重复通知、不可变回复、崩溃恢复、未知动作不重做、CRC/显式已读验收。固定秒数目标待基线和试验后再定。

## 拒绝项

拒绝删除持久进度/SQLite同步、claim 自动过期重领、缩短不确定通知宽限、并行竞速两个执行器、用暂定转写触发动作，以及未经验证的原 Bot API 替代承诺（A:103–117；B:79–89）。也拒绝把 beam1 的不同文本视为等质量加速、把 0.2 秒轮询或约 12 毫秒渲染当作当前主要瓶颈、把删除两次快速 MCP 调用承诺为节省全部中间空档。
