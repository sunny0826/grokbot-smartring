# 候选 A：保留原「毛线」Bot，先缩短串行关键路径，再决定是否流式化

## 范围、证据和结论

只读设计，未改产品、未调用业务服务、未驱动应用、未做性能实测。基线 HEAD `0b608293ce121be869110a5aa0f571bc65c4ddc7`，分析包含工作区内未提交的自动唤醒实现（notifier、trigger、routine、store、cli 等）。已读取 architect/how 及 architect 的 runner、principles、red-flags、rationale。已做一次定向 Nowledge 搜索：历史确认过 5.455 秒合成 WAV 经真实 webhook→原 Bot→MCP→回复，总体约一分钟；缺阶段时间，不能当作实物录音的性能基线或归因。

优先选择保留原 Bot 的方案。当前明显是“多阶段串行 + 外部 Agent 多轮工具调用”的架构。独立源码分析后，主协调者补充了下述真实请求时序和隔离ASR测量，已足以把本轮优化重点放在云端编排/工具往返，而不是优先更换Whisper；仍不能把全部云端间隙归因于模型思考或Cloudflare。最应避免的是看到 120 秒就把重试调短，或直接换一个无原记忆和工具的模型。

M4 16GB 的隔离同样本5轮交错测试：当前base CPU int8转写中位0.876秒，范围0.678–1.057秒；指定中文约0.6秒；beam1约0.458秒，但关键词由错误的“圓平”变为同样错误的“原平”，目标“圆屏”。这只是一个合成样本的热转写对照，不能代表所有语音准确率或冷启动。它说明本样本改ASR预计只涉及不到一秒量级，不能解释/解决已观测30–40秒的通知后链路。

据此优先级修订：第一优先记录通知HTTP接受时间并获取Bot原生执行trace，缩短重复发现、在线确认及确定性状态保存造成的Agent回合；第二优先设备第一页预取；ASR参数只作为低收益且需准确率验证的后续项。若固定mailbox调用仍需要动态设备实例ID，必须有稳定ID映射/重连失效恢复，不能简单删掉发现步骤导致找不到设备。

## 用户实际用法与观测终点

用户按结束录音后，期望尽快看到正确回复；应分别测：

1. 结束录音 → 上传已持久化；
2. 结束录音 → 回复已持久化；
3. 结束录音 → 屏幕提示可查看；
4. 点击查看 → 第一页真正显示。

第 2 项是处理速度，第 3、4 项是设备体验。用户点击前的停顿不能算入后端耗时。当前回复保存好后不会自动下载正文，点击才下载页（`firmware/grokbot/main/voice.cpp:173`）。建议自动预取第一页，仍由用户决定何时打开；预取不能自动标记已读。

## 当前数据与状态所有者

```
ESP32 录音（48k PCM16，完整存 PSRAM）
 → 完整 WAV HTTPS PUT（稳定 request_id）
 → Mac Server 校验并 Store SQLite 持久化 stored
 → 单 Worker：transcribing → ready
 → 独立 Notifier：webhook 唤醒原毛线 routine
 → 原毛线经现有 grok-gadgets MCP 领取 claim + 转写正文
 → 原毛线思考/调用既有工具
 → MCP voice.reply → Mac 渲染全部页面并持久化 replied
 → ESP32 状态轮询 → 用户打开 → 下载 RGB565 页
```

SQLite Store 是任务、claim、不可变回复、页面、通知重试状态的唯一拥有者。Bot 拥有工具执行的进度和外部动作结果；这两类状态不可粗暴合并成一个“处理中”标志。设备只拥有本地录音、请求 ID、显示及用户已读动作。

本地 ASR worker 和 notifier 已是不同线程，不存在“等 webhook 完成才能继续转写”的串行关系；每条任务本身仍必须先转写，再唤醒 Bot。Python HTTP 服务是受限并发线程，每个请求一个 TLS 连接；当前服务主动 `Connection: close`（`server.py:86`），固件每次创建并清理 HTTP 客户端（`voice_http.cpp:24,63`）。

## 已确认的延迟来源与不确定项

| 阶段 | 代码事实 | 判断 |
|---|---|---|
| 音频上传 | 48k mono16；96KB/s，5秒约480KB，30秒约2.88MB；完整 body 后才存储（`voice_logic.h:8`, `server.py:132`） | 真实字节量确定，上传时间未知；设备远程隧道与 LAN 必须分开测 |
| ASR | `base` CPU int8；首次调用加载模型；VAD；未显式设语言和 beam 等（`worker.py:6`） | 冷启动与正常转写分开；不应把未显式设置的依赖默认值当作本项目优化结论 |
| 预加载 | `--preload-model` 加载后进程退出，正常服务重新构造懒加载对象（`cli.py:81,99`） | 已缓存下载文件不等于服务内模型已预热 |
| worker/notifier | 空队列各等待0.2秒（`worker.py:45`, `notifier.py:45`） | 正常健康情况下只引入亚秒级调度等待，不足独立解释一分钟 |
| 唤醒 | 首次 ready 可立即通知；全局最小通知间隔15秒（`store.py:170`） | 连续语音可能被明显延后；不是孤立首请求固定15秒 |
| 通知120秒 | accepted/uncertain 后再次发通知的宽限（`notifier.py:27`） | 不是收到成功回执后必须等120秒；缩短会增加重复 routine |
| Agent | routine 要确认信箱、持久化 claim_id 和进度、claim、处理、reply；已避免先 read 正文（`grok-routine.txt:5`） | 多次模型/工具往返可能重要，但没有运行轨迹不能给占比 |
| 本地邮箱 | TCP poll0.2秒，state刷新1秒（`mailbox.py:144`） | MCP 命令返回路径与 state快照不同；不能把1秒刷新当所有 command 必等 |
| reply落库 | 首次字体加载、全部页渲染在同一 Store RLock 内（`store.py:270`） | 会阻塞其他状态读写；单请求绝对成本仍待测 |
| 页渲染 | 每页272×168×2+16=91408字节；Python逐像素转换（`render.py:60`） | 有可优化点，不能先声称是主瓶颈 |
| 设备 | 活跃2秒、idle5秒轮询，间隔在上次响应后设置（`voice.cpp:333`） | 额外感知延迟可达一个周期加网络时间；不是严格“最多2秒” |

`server.py` 的日志被关闭，任务表没有创建、ready、claimed、replied 时间。notify_last_at 只记录最近通知尝试，不能完整重建流水线。缺少完整 Bot routine 执行轨迹、模型/工具时长、真实设备网络吞吐，因此本方案不承诺固定秒数。

## 方案 A 的具体结构

### A0：让每次请求自己解释时间花在哪

保留 request_id 贯穿设备、本地服务、通知和 Bot。新增小型 append-only 阶段记录，记录阶段、attempt、起止时间、结果、字节/音频时长；不记录音频正文、转写全文或凭据。耗时用所在进程的 monotonic clock，跨进程关联用 UTC 和 request_id，不能直接相减未校准的设备与 Mac 时钟。

最低需要：device_stop/upload_begin/upload_ack；body_received/stored；asr_start/model_ready/asr_done；notify_reserved/notify_result；claim_received；reply_received/render_done/reply_committed；device_reply_seen/page_downloaded/displayed。cloud 部分先用 notify接受→claim 与 claim→reply 分段，这两段分别包含调度/发现/claim 和实际处理/回写；没有 Bot 原生 trace 时不能再冒充精确拆分。若可取例行任务工具 trace，再关联每个工具 call 与 command_id。避免为日志额外增加 Bot 工具回合。

### A1：消除可确定的重复工作和首请求额外成本

1. 正常服务启动时创建并加载一个长期存活的 transcriber，显式报告 ASR readiness；字体 renderer 同样预加载。只迁移冷启动成本，不声称所有请求都会同样加速。可以先保持 HTTPS收音、排队，但对设备如实显示准备中。
2. 给固定中文输入做可回退的语言配置；有英文/混合语言需求则保留自动检测。对同一批真实音频比较解码参数，先验证人名、地点、数字、否定词和命令意图，再选择参数。CPU线程、beam、更小模型或不同后端是实验变量，不是未经证明的默认改动。
3. 当前 routine 已把第一页转写合并进 claim，保留这点。固定 mailbox/capability 与任务定位，核查真实 trace 是否每次重复列表/发现设备；可把在线检查交给实际 claim 错误响应，减少无必要调用。`gadgets_command` 若已返回终态直接使用；只有 accepted/dispatched 才查 status。不得用设备最新 state 代替当前 command 的关联回执。
4. 保留唯一claim、动作前持久化started、结果不明时核对、同文reply重试。可以把确定性的校验/claim ID生成/状态推进移至已有执行环境的代码适配层，但必须先确认原 Bot 支持的运行接口与持久化能力；不能凭空声称已有 SDK。纯问答不必逐个模拟外部动作检查点，有外部副作用的任务仍保留。

### A2：处理队列和设备体验

1. 将15秒全局间隔拆成“新请求首次通知”和“同一请求重试”政策。首次请求使用受上游限制约束的小突发/速率控制；重试保留指数退避、Retry-After、未知投递宽限。只有测得连续请求被该门槛阻塞才优先实施，不能无节制并发唤醒同一 Bot。
2. Store commit 后发进程内 event/condition 唤醒 worker/notifier，保留数据库为事实源，启动扫描恢复，避免通知丢失；收益上限是原0.2秒等待，主要降低无用唤醒，不是主性能项目。
3. `replied` 被设备发现后预取第一页并缓存，点击即时展示；新请求或配置变化时清理正确缓存。前台可适度提高轮询频率，但 TLS开销会增加。更合理的后续结构是有限期 long-poll 或由现有控制连接通知“状态可能变了”，设备仍通过认证 HTTPS 拉取最终状态/页面。推送丢失时退回轮询。不要把回复正文塞进2KB设备控制帧。
4. 将渲染移出全局数据库锁。最小设计：锁内验证并读取不可变 claim；锁外 render；锁内重新核验 claim/无reply/容量，原子提交页面与reply。同文并发可能重复渲染但只提交一次，不同文竞争只能有一个成功。若需要避免重复渲染，再引入每request渲染协调，别先扩大状态机。font对象线程安全必须确认或用专用渲染线程。不能在页面未完成时提前返回 `replied`。

### A3：仅在测量证明后改较贵路径

录音降到16k mono16可使相同秒数 PCM字节数变为三分之一，但需要 ESP32正确降采样/抗混叠、WAV协议版本或兼容变更、服务验收和 ASR准确率验证；直接每三个采样取一个有混叠风险。压缩需要额外编码CPU和解码依赖。网络上传占比小就不值得先做。

Mac上的替代ASR后端（例如适用硬件加速的实现）只能作为候选实验，需先确认机器芯片、依赖支持、内存和准确率。增加 ASR worker 适合队列等待明显的多请求情形，不会天然加速单条转写，反而可能争CPU/内存。

## 结构不同的备选

### B：录音与转写重叠，仍由原毛线最终处理

设备将带序号、request_id 的音频块持续送 Mac；Mac拥有接收会话与暂定转写，用户结束后 finalize，生成不可变最终正文，再进入原有 ready→notify→claim→reply。该方案把上传与部分ASR工作移到用户说话期间，主要降低“松手后”等待；Bot链路不变。

公开接口可为 `open_recording(id,format)` / `append_audio(id,seq,digest,chunk)` / `finalize(id,last_seq,digest)`，设备无需知道 ASR内部状态。分块去重、缺片、重连、取消、会话超时、finalize重试由 Mac负责。暂定文本不能触发有副作用动作，最终音频及正文持久化后才能激活。当前 faster-whisper 调用是完整文件接口，不等于支持真流式，需选择真实增量实现或窗口重转写并测额外工作。成本较高，适合长录音且上传/转写占大头；若 Bot调度占大头收益有限。

### C：直连推理/动作编排器，旁路原 Bot例行任务

Mac完成ASR后直接调用模型服务，再复用本地回复流程，控制权与Agent状态归Mac编排器，能减少 webhook调度与通用MCP取件回合。但是原毛线的会话记忆、工具、身份、权限并不自动迁移。即使用同一家模型 API 也不等于“同一个Bot”。用户尚未允许旁路，因此仅列作需明确选择的产品方案。

若原 Bot有经确认的正式低延迟会话/消息接口且保留同一记忆与工具，可用专用适配器替换 routine唤醒；这是比另建模型更符合约束的方向，但目前未验证此能力。不能调用未证实的接口设计冒充可落地方案。

混合路由（简单问答直连、复杂任务原Bot）额外引入路由错误、记忆分叉、双重执行与重试责任；不应在用户未明确选择前实施。确定性本地功能如显示天气缓存也必须界定权威数据、失效和权限，不能用“简单”取代安全判定。

## 选择与实施顺序

建议 A 为基础，按补充运行证据，先 A0 与 A1 的例行任务往返核查/减少固定管理回合，再考虑进程预热；并行评估首屏预取，但保持产品工作本轮只设计。两次真实链路已显示 notify预留→claim与claim→reply均有秒至十秒量级间隙，本地claim/reply本身亚秒，因此优先调查Bot调度/发现/持久进度与推理/业务工具，而不是先优化0.2秒poll。仍需补齐notify接受时间与Bottrace才能细分。连续请求被15秒门槛卡住→调首次通知政策。A2只在对应现象下做，B等待音频段证据，C等待用户产品选择及接口验证。

不推荐为了速度去掉SQLite持久化、调低磁盘同步、自动让claim过期重领、缩短未知投递重试、并发执行同一请求、把 webhook接受当回复成功。这些都可能用正确性换表面速度，且未有证据说明持久化是主要成本。

## 可测验收

先收集真实设备短句/长句、普通问答/带工具动作、冷启动/热运行、LAN/远程、单条/连续两条，使用相同样本比较优化前后。不要复用真实副作用任务反复执行；动作路径使用明确测试对象。至少报告样本数、每段中位数与尾部、失败/重试次数、ASR关键语义正确率，以及用户按键到可查看和点击到显示两项。

单次一分钟样本不能定P95或承诺“优化到几秒”。先制定相对接受标准：对应目标阶段有稳定下降；关键语义和任务成功率不退化；重复上传、重复webhook、claim回执丢失、reply回执丢失、渲染期间重启与网络断开后仍收敛至一个不可变回复；任何外部动作不能因优化新增重复执行。每项优化独立对照，一次不混入ASR换引擎、协议改版与Bot改流程，以免失去归因。
