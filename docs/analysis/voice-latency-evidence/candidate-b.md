# 独立候选 B：保留原 Bot，以阶段证据驱动缩短关键路径

本候选为只读架构分析，没有改动产品、配置、例行任务或运行服务，也没有新测量真实延迟。分析基于 HEAD `0b608293ce121be869110a5aa0f571bc65c4ddc7` 及当前未提交工作区：包含新增 notifier.py、trigger.py、grok-routine.txt，不能把 HEAD 单独当作运行版本。已读 architect 的原则、风险检查、设计请求及 how。已定向搜索 Nowledge Mem，2026-10-17 实测记录只支持“5.455 秒合成语音约一分钟达到 replied”；它不是实体麦克风测量，也不能拆分一分钟的阶段占比。用户当前确认真实链路已通。

## 结论与共同约束

当前是完整录音之后依次上传、转写、唤醒原 Bot、由模型多轮调用 MCP、保存完整回复、圆屏轮询后加载图页的串行流程。单用户正常请求不一定被 Python 单线程拖慢：只有转写线程单工，HTTPS、通知、MCP 信箱各有线程。结合主协调者新提供的实测证据，目前优化重点应为原 Bot 被唤醒后到提交回复的阶段，而不是先更换 Whisper；具体是平台调度、模型推理还是进度保存，仍不能凭空拆分。

默认保留原「毛线」Bot 的记忆、工具、权限和对话结果，不把普通问题偷偷交给另一套模型。保留 claim 独占、同文回复幂等、动作结果未知时不重做。目标同时测“松开/发送到回复可取”“回复可取到屏幕可见”和成功率。用户点击查看的等待不能算作后端处理时间。

## 已核实的运行模型

1. 固件完整采集 48 kHz、16-bit、mono WAV，录音停止后 `send()` 才调用同步上传（voice.cpp:158；voice_logic.h:8；voice_transport.cpp:24）。每秒 96,000 字节，30 秒音频 2,880,044 字节含 WAV 头。服务器必须读完整请求体并严格验证 48 kHz，再一次性写 SQLite（server.py:17、122；store.py:113）。
2. Store 同一进程持有一条 SQLite 连接和 RLock，音频、转写、任务状态都在 jobs；页数据在 pages。FULL/fullfsync 保证持久性。Worker 每 0.2 秒发现 stored，改成 transcribing，在锁外推理，完成后改 ready（worker.py:36；store.py:138）。因此转写计算没有持有数据库全局锁。
3. faster-whisper 默认 base / CPU / int8，模型第一次调用才加载（worker.py:6–20）。`--preload-model` 实际加载后退出，能预下载缓存，却没有给之后的服务进程驻留模型（cli.py:81–87、99）。一次冷请求包含模型导入、加载、可能的首次计算开销。
4. ready 入库即标记通知 pending；独立 Notifier 0.2 秒查找任务，HTTPS POST 唤醒原例行任务（store.py:145；notifier.py:22、37）。**120 秒是 accepted/uncertain 的再次触发宽限，不是首次通知等待**。全局最小触发间隔为 15 秒，连续多条/其他重试会相互影响（store.py:170–192）。HTTP 200 仅表示触发被接受，不等于例行任务已启动或完成。
5. 例行任务需要确认信箱在线、持久保存 request_id/claim_id、voice.claim、读取该 command 的结果；pending 才查询 command_status。claim 已附前 800 字符转写，不应再无条件 voice.read。外部动作前后保存进度，用于防重复；最终 voice.reply。可见 grok-routine.txt:步骤 1–7。Bot 执行器的排队、模型轮次、实际工具调用和进度保存方式不在本仓库，不能仅由提示词推定真实执行次数。
6. 信箱是现有网关的真实软件设备，通过 loopback TCP 常连接每 0.2 秒 poll、每 1 秒上报 state（mailbox.py:129）。每项 MCP 命令可能含云端工具往返与模型下一轮调度，不能只按本地 0.2 秒推算。
7. voice.reply 在 Store 全局锁/事务中首次加载字体并渲染，完成全部页和回复原子提交才变 replied（store.py:265–302）。字体对象会复用；不是每条回复都重新加载。RGB565 转换是逐像素 Python 循环（render.py:60–64）。这会阻塞同期状态查询和其他写入，但尚未测量，不足以解释一分钟。
8. 固件活跃请求每次 HTTP 完成后再等待 2 秒，空闲 inbox 等 5 秒（voice.cpp:333–351）。因此不是严格每两秒请求一次，网络 RTT/握手耗时还会叠加。服务器每次响应都 `Connection: close`（server.py:92），固件每次创建/销毁 HTTP client（voice_http.cpp:55、63），每次状态/页读取均重建连接。单纯把 poll 缩到 0.2 秒会大幅增加握手和资源占用。
9. 页面为 272×168×2 + 16 = 91,408 字节；回复可取后用户点击才下载当前页（voice.cpp:173、约190–204）。当前 UI 的 Waiting 仍显示“在 Bot 中说 处理圆屏语音”（voice_ui.cpp:241），与自动触发实际能力不符。这是需要修正的状态文案，不是性能提升。

一个附带成本：Store `_row` 使用 `SELECT *`，状态 GET 随之读取整个 audio BLOB（store.py:92、105）；inbox 也用 SELECT *（304）。建议窄列读取元数据，不能把它夸大为已证实的主瓶颈。

主协调者在 M4 16 GB 隔离重放同一5.455秒合成样本，现行base CPU int8暖态中位约0.876秒，范围0.678–1.057秒，五次；固定中文约0.6秒，beam1约0.458秒但文本也改变，目标“圆屏”仍未正确识别。此结果支持暂缓改模型优先级，不代表真实麦克风所有任务都是一秒，也不能用不同文本的0.458秒直接承诺同等准确率性能提升。

因此首选先核对实际 list/get_state 是否确属例行任务必须步骤，删去可由直接claim回执代替的重复发现；并调查持久进度是否引入多余模型轮次。四次可见MCP操作本身都很快，不代表删除两次工具一定减少其间全部空档，收益须做同类型端到端对照。

## 推荐基础方案：保持执行边界，削减已定位的等待

调用者继续只做三件事：设备上传一个 request_id 并查询状态；Bot claim 指定请求、按需调用原工具、提交一次回复；设备查看/明确已读。协议内部的计时、预热、调度、连接管理对调用者隐藏。

### P0：先把一分钟拆开

新增统一的 request_id 阶段事件，保存数值和原因，不记音频/转写全文、凭据或 URL：

`recording_stopped → upload_started → upload_accepted → asr_started → model_ready → asr_done/ready → trigger_started → trigger_accepted → claim_committed → reply_received → render_done → reply_committed → device_observed → first_page_visible`。

Mac 用单调时钟计算同进程 duration，另存 wall clock 和 process boot id 供关联。设备同样本地单调计时；跨机器绝不能直接相减未校准 wall clock。Bot 可观测的启动/首工具/外部动作起止若平台支持，单独采集；否则 `trigger_accepted→claim_committed` 是包含平台排队、模型准备、发现与领取的黑盒，不命名为纯“云端排队”。`claim→reply_received` 也含思考、工具和进度保存。

Store 是任务状态的唯一写入者；阶段事件在状态事务中记录，度量线程不得改任务状态。设备可以用小型回执报告 observed/visible，失败不阻断任务；未落地前用固件串口时间作验证即可。建议不先建设复杂监控平台。

### P1：先优化 Bot 编排，再做低复杂度本地改善

- **服务进程实际预热**：创建并加载同一个 WhisperTranscriber，然后交给 Worker；字体 RenderPages 同样在接收工作前初始化。报告服务就绪/故障；模型文件不存在时明确失败，运行期不突然下载。收益仅针对冷加载部分，不能消除稳态推理。真实样本检验首次推理是否仍有额外冷开销。
- **状态查询不读音频**：Store metadata 查询列固定，只让转写 worker 取音频；不为此拆数据库。容量统计若样本证明明显耗时，再维护同事务的存储计数，避免增加同步义务。
- **清理实际发生的多余模型工具往返**：从真实例行任务轨迹找是否重复 list_devices/get_state/read，是否不必要地反复 command_status、做全文/网页检索。已知 mailbox_id，可探讨直接 claim 并以其明确在线/失败结果替代每条发现；若现有 MCP 契约要求先发现则保留。保持指定 request_id、命令回执、正确 claim_id、按需分页，不删除动作前的持久进度。纯问答无外部动作时不制造 started/action-result 步骤。已有提示词禁止不必要的 voice.read，不能把重复写同样提示词当优化。
- **状态展示诚实**：ready 区分通知待发/已接受/重试/暂停，claimed 显示已接单，错误明确阶段。可选显示耗时。不要显示未经测量的预计完成秒数；不把“收到”当最终回答写入不可变 reply。

### P2：由阶段占比决定的定向改动

若 ASR 占主要时间：建立相同真实中文录音 corpus，比较当前 base 配置、明确语言后的配置、较小模型或适配机器的其他后端。比较字符错误率及实体/数字/否定等关键语义，排除因提前截断、空转写、VAD 切掉语音造成的假加速。可以设置常用语言但保留多语言需求；不要为降时延默认牺牲用户实用准确率。只有排队时间显著才增加有限 ASR 并发，检查 CPU 竞争和内存；单用户请求加 worker 通常不能加速单次推理。

若 trigger→claim 或 claim→reply 占主要时间：重点精简例行任务的机械步骤与实际工具轮次，先测普通回答和需要原工具的任务。若平台提供官方的同 Bot 定向执行、工具调用可等待 ack、可选择推理档位等接口，再在真实契约内讨论；当前仓库不能证明这些可用。不要用未验证的“直接 API”作为马上可实现的承诺，也不能把另一 API 模型等同原 Bot。

若并发下渲染锁等待可见：两阶段 `prepare_reply`。短事务先确认 claim 与不可变回复约束；锁外计算页面；短事务重新确认 claim/status/text、重新检查容量，再把 reply 和全部 pages 原子提交。两线程同文重试即使重复渲染也只能提交一次，异文必须冲突；崩溃前回复没有发布，原 claim 保留。此方案保留现有 replied=完整页可取契约，不需要先引入 replied_but_rendering 新状态。测量证明逐像素转换占比高后再换批量转换，并比较逐字节页面、CRC、颜色、缺字和换行。

若设备尾延迟明显：先实现客户端连接复用并同步调整 server 的关闭策略和空闲连接上限；不能只改一端。当前16个线程槽会被长连接占用，需要限制每设备连接/空闲超时并验证重连、设置切换、TLS认证撤销。然后可在等待界面短周期轮询，回到空闲降频。更进一步考虑有界长轮询或复用已有设备控制通道发“有回复”提示，仍以 HTTPS 状态为权威；不要为一块屏马上新增 WebSocket 常连接协议。回复就绪后可预取首屏，用户点击直接显示；预取不能自动标记已读。

若连续多条明显卡在15秒门限：区分“从未发送的新请求”和“同请求不确定重试”，保留失败退避与服务端 Retry-After，在确认平台频率限制后给首次通知有限突发容量。重试不能占满新请求公平性；若必须全局限流，向设备显示队列等待。不要盲目删掉15秒和120秒两个保护，也不要提高重发频率来掩盖 Bot 启动慢。

## 结构上不同的备选

### B2：本机流式接收与推测转写，Bot仍只处理最终录音

把当前“完整 audio BLOB 一次存入”的形状改成 `recording_session + 有序音频块 + finalized_digest`。设备边录边传，Mac 增量识别；只有明确 finish、完整验证、最终转写提交后才触发原 Bot。录音会话拥有块序号、去重和结束判定，业务请求仍由 Store 单独持有；取消和未完成录音不能触发动作。

这是把上传和部分识别移到录音时间内的实质结构变化，可以减少用户松手之后的剩余等待，但不能减少云端 Bot 阶段。代价是固件录音与网络并发、背压/断线恢复、PSRAM、分块持久化与识别上下文合并。需要区分局部转写和最终文本，绝不能用不稳定 partial 执行外部动作。只有长语音上传/ASR 确实占主导才值得选。若需求仅弱网传输，先比较16 kHz适当抗混叠降采样，线性PCM字节量可减至1/3；当前服务器严格48 kHz，需要协调修改协议验证和测试，不能单改采样常量，也不保证推理时间同比减少。

### B3：确定性本地编排器 + 原 Bot作为执行端（条件方案）

本地编排器承担 request/claim/dispatch/result 的机械协议，原 Bot只拿一条已登记任务执行，再返回确定性结果；可减少让模型多轮“找信箱、领取、保存进度、查状态”的机会。成立前提是平台有受支持的同 Bot 定向运行接口、稳定 run_id、回调/查询结果和重试契约。当前源码没有这种证据；仅 webhook唤醒不能推出以上能力。若不存在，不选择此方案。

即使存在，本地 claim 排他也不等于外部动作 exactly once：本地 ledger 无法与第三方动作原子提交。必须复用工具原生幂等键、保存动作结果，并将未知动作标为待核对。不得以“服务器负责”名义删除现有防重复语义。

### B4：简单问答快速通道 + 原 Bot处理有记忆/工具的请求（授权未定）

路由器本地或直接模型回答简单问题，仅复杂问题交原 Bot，会改变回答主体、记忆可见性、模型能力、隐私和会话一致性。可以是另一产品取舍，但当前不能默认采用。并行启动两个执行器后选先返回更危险：即使答案只用一个，外部动作可能已做两次。若用户未来允许，也必须在独占 claim 前完成受约束路由，外部动作永远只由一个执行所有者完成；置信度不足回原 Bot，不假装拥有原 Bot 记忆。

## 设计接口草图（未实现）

外部调用保持 `put_recording(request_id, device_id, audio)`、`claim_request(request_id, claim_id)`、`reply_request(request_id, claim_id, text)`；claim_id仍由独立运行生成，同一运行重试复用，不能仅按request_id派生给不同运行共享。

内部建议 `JobStageEvent(request_id, stage, duration_ms, occurred_at, process_id, outcome)`；`warm_resources(model, font) -> RuntimeResources`；`render_reply(text, immutable_render_spec) -> RenderedReply`；`commit_reply_if_claimed(request_id, claim_id, text, pages) -> ReplyResult`。Store拥有持久状态与原子提交；Transcriber拥有模型；Renderer拥有字体与版式；传输层拥有连接和重试而无业务完成权限。错误继续按上传/ASR/通知/领取/处理/渲染/显示区分，异步未完成不冒充成功。

## 验证与决策门槛

先用真实麦克风样本与相同录音重放建立基线：短句、长句、含数字/专名、需要记忆、需要只读工具、需要外部动作；冷服务与暖服务分开、单请求与连续多条分开、LAN与远程网络分开。每类重复足够次数，报告样本数、原始分位数和失败率；小样本不能把p95当稳定承诺。不得把合成短句替代整个用户场景。

每一轮只改变一个关键因素，记录各阶段 p50/p95、总时延、ASR质量、CPU/内存、模型轮次/MCP调用数、网络请求与连接数。保留所有请求，包括失败与重试，不能只比较成功且缓存命中的样本。端到端测到首屏实际可见，再另报可取时刻，不混入用户点击等待。

必须回归：相同上传幂等、不同音频同ID冲突；不同运行claim竞争；claim成功回执丢失；重复通知；回复同文重试/异文冲突；ASR重启恢复；渲染前中后崩溃；外部动作结果未知不重做；页面CRC与显式已读。所有加速必须在这些行为保持时才算成立。

推荐实施顺序：补齐阶段计时并纠正状态文案 → 验证并减少Bot发现/领取前的重复轮次 → 同进程预热及窄列查询作为次要改善 → 按新证据决定锁外渲染/连接复用/首屏预取 → 最后决定是否需要流式结构或另一路回答主体。现有实测下，不把替换ASR或流式化列为主线。没有阶段测量前，不承诺“从一分钟降到十秒”，不引入Redis、多服务队列或多模型竞速。
