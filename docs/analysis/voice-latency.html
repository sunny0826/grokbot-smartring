推荐的执行顺序

先精简「毛线」的正常路径

直接领取已知信箱的指定请求；把列设备、读状态移到异常恢复。保留领取凭证和防重复动作规则，同时记录每段耗时。

让回复到达后的体验更直接

前台等待时预取并展示首屏；后台保留未读提示。修正旧的手动处理提示，明确显示当前阶段。

再按测量调整本机与传输

服务进程内预热，测试中文语言提示。只有上传或 TLS 明显拖慢时，再做降采样和连接复用。

为什么不直接调小 120 秒

120 秒是通知成功或投递不确定后的重试保护。这两次都一次触发成功，没有等重试。调小只可能重复唤醒 Bot。另有 15 秒全局发送间隔，影响连续请求；它也未拖慢这两次相隔数分钟的请求。

为什么不马上换模型、做流式或绕开毛线

当前本机转写不足一秒，流式上传无法消除后面的云端等待。直接模型 API 可以改变执行路径，但不会自动继承毛线的记忆、工具和权限。这是另一项产品选择。

现在还不知道什么

缺少按键释放到首屏的完整计时、上传耗时及云端内部各步骤耗时。两次线上记录不能代表 p95，也不能承诺改完固定几秒返回。下一步应做同类请求的修改前后对照。
