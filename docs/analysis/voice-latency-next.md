# 圆屏 → 原 Grok Bot → 圆屏：下一轮延迟方案

2026-10-17。分析基于 HEAD `759f03c`；开始时工作区干净。本轮只读源码、既有生产计时与官方资料，新增分析产物，没有发送测试语音、修改服务、云端任务或固件。[图示摘要](voice-latency-next.html)。

**结论：主要等待仍在通知后的云端阶段。先测到实体首屏，优化设备交付，再对照试验通知携带转写。省掉领取回合有更大结构潜力，但当前缺少执行权限隔离的证据，不能默认上线。**

默认保留原毛线的记忆、工具和授权机制。首句／完整回复的偏好尚未收到回答，因此两个指标都保留；“收到”“处理中”和动画反馈均不算有效答案。

## 2. 已完成的优化，不重复计入新方案

- 原 Bot 正常路径已经是 `voice.claim → voice.reply`；此前五次工具记录不再有list/get_state。
- 同进程模型／字体预热、窄列状态读取、分段计时已实施。
- 前台等待回复已经自动打开；主页／设置遮挡时不抢占。见 `voice_ui.cpp:333`。
- 已读异步化改善点击体验，不会减少云端生成回复耗时。

当前链路为：完整录音上传 → 本机转写 → webhook仅带定位ID → 原Bot领取并取得正文 → 生成答案／执行任务 → 保存不可变回复 → 圆屏查询状态 → 另取RGB565首屏 → 显示。

## 3. 推荐推进顺序

### 第一步：补齐用户真正等待的时间

固件按request_id记录松手、连接完成、上传确认、状态变为replied、页面校验完成、包含答案的显示刷新完成。需要关联页面代次和最后一条显示传输完成，不能以UI状态切换代替上屏。每台机器分别用单调时钟计时，不直接相减未同步的设备／Mac时钟。

两个验收指标：松手→首句有效答案上屏，以及松手→完整答案可读。当前最多128字单次回复时，两者通常接近；多页以完整答案可获取与实际阅读分开，不把用户翻页时间算作模型延迟。

仅记录阶段、ID、长度、错误与重试次数。此步没有直接省时收益，但决定后续改动是否真有收益。

### 第二步：减少回复保存后的设备空等

源码确认 `voice.cpp:144`在每次成功状态请求后再等2秒；`voice_http.cpp`每次新建并销毁HTTP客户端，`server.py:105`强制Connection:close；`voice_page_transport.cpp`另建连接下载首屏。

先测连接耗时，再按证据依次试验：

1. 在同一端点／凭据scope内复用HTTPS连接。前台请求与后台信箱不能并发使用同一客户端；网络／scope变化必须失效并重建。服务端有界空闲超时和连接配额，不能仅删除Connection:close。
2. 增加有界“等待回复就绪并返回首屏”请求，减少2秒轮询空档和状态→取页的额外往返；响应携带request_id、page_count、版本及完整首屏校验信息。没有结果时返回可区分的等待状态，断线仍按request_id恢复。
3. 等待请求不能持有Store锁，也不能占满服务端16个线程槽；设置独立等待配额，保留上传／确认容量。固件网络等待须可取消或由独立网络任务承担，保留返回主页、设置切换和后台不抢占行为。

**收益边界：仅定时空等约0–2秒；TLS、首屏传输收益尚未测得。** 多次轮询握手可能与云端处理重叠，不能把每次握手耗时累加为端到端收益。连接复用由[ESP-IDF 5.5.3官方接口](https://docs.espressif.com/projects/esp-idf/en/v5.5.3/esp32s3/api-reference/protocols/esp_http_client.html)支持，要求复用handle且服务端允许保持连接；这不是本项目收益证明。

### 第三步：让原Bot从通知起就知道问题，做小规模对照

当前 `trigger.py:99`仅发送event/version/request_id/mailbox_id。可把已落库、不可变的短转写随通知一起发送，带转写版本／摘要，长文本明确走现有领取分页路径，不静默截断后执行。

保留claim：通知文本用于预读，claim关联回执是权威正文和执行权；一致性校验失败时仅用权威内容。Bot仍须领取成功后才调用业务工具，冲突即停止。需同步修改现有routine的“请求体只用于定位”规则，不能只改本地payload。

官方确认[webhook JSON随routine指令传给Bot](https://cursor.com/help/grok-bot/routines)，因此机制可行；提前看到问题是否改变实际推理／调度尚未证实。**这一步没有减少工具调用次数，不承诺省一个完整回合。** 短答案优先提交已是现状，不再算新增收益。转写仍发给原Bot，但通知体会新增语音正文，日志及错误处理不得记录完整body。

### 实验备选：纯问答一次原子提交

可在隔离原型中比较 `通知带正文 → 原Bot生成答案 → voice.answer(request_id, operation_id, transcript_version, text)`。由Mac在一个事务内验证ready和版本、原子占有并保存回复；不同run使用不同operation_id，同操作同文重试返回原结果，异文或已被别人领取均冲突，不覆盖历史回复。首屏仍走既有replied状态，避免两套最终回复事实来源。

这有机会省去“claim获取正文→模型再继续”的依赖回合；但生成答案本身不能消失，不能直接把10.315秒当收益。也无法消除云端最初启动／调度等待。

**当前不建议默认启用。** 原毛线持有记忆和外部工具，本地原子保存只能保证一份回复，无法阻止两个云端run在提交前都发消息或写记忆。提示词分类不是硬权限隔离。目前没有已验证的每run工具隔离能力；必须先证明快路在提交前不能产生副作用。否则保留claim路径。不要把同一个claim_id塞进webhook让重复run共享执行权。

### 后置项目

- 边录边传：只有真实上传成为显著占比时再做。分块带序号／摘要，最终commit后才触发处理；取消、断线未commit不得启动Bot。最新1.876秒body读取说明有空间，不等于能省完整1.876秒，更不等于省录音时长。
- 16kHz上传：当前服务端严格校验48kHz，须同步协议和设备重采样，不能仅改WAV头。先验真实语音识别质量，当前ASR不足1秒，不优先换模型。
- 分段答案／token流：当前回复不可变且最多128字，新增分段会扩展持久状态、翻页、恢复和已读语义；尚无收益证据，本轮不推荐。
- 缩短120秒重试或重复webhook竞速：本批记录只通知一次成功，改重试不能解决现有正常延迟，反而增加重复运行。
- 更换“更快模型”：[官方FAQ](https://cursor.com/help/grok-bot/faqs)明确原Bot没有模型选择器。另起直接模型API不能假定继承毛线记忆／工具，不是当前默认方案。

## 4. 验证与实施分解

每个改动分别比较，相同录音、相同预期答案、同网络路径与合理生产配置，旧新每侧至少5次交错。冷暖连接、LAN／远程、纯问答／动作任务分组，不混报。报告中位数、范围、样本数、失败与重试；五次不用于宣称稳定尾延迟。

验证答案内容及实体上屏，不能只看200／退出码。注入重复通知、双run争用、领取和reply丢ACK、重启、断网、scope变化、等待槽耗尽；已读与后台不抢占行为也要保持。外部操作用可计数替身验证重复抑制；动作成功后崩溃且无幂等键时，仍须核对结果，不能声称恰好一次。

依赖：先计时基线，再逐项设备优化；通知预送文本可独立试验。Mac SQLite仍是唯一状态所有者，云端只通过工具写入，固件只负责录音／读取／显示；server.py等共享文件实施时指定单一写者，不同时改部署实例。原子回答实验依赖权限隔离证明，不能跳过。每个单元保留可回滚配置／协议回退，验完再进入下一项。

本轮只做分析，故未执行新生产A/B、固件烧录、云端指令更新及行为回归；这些属于后续实施验收。

## 5. 方案比较与证据强度

按rigor的性能流程，以“解释数字”原则排除把read当显示、把云端间隙全算模型、把不同输入当AB；以数据归属原则保留SQLite单一最终状态，减少复杂度原则将分段回复后置。

两个全新独立候选会话、一个候选完成后启动的独立评判会话均继承当前模型（同模型，不是跨模型验证），只读设计、无产品写入：

- A：通知带正文＋纯回答原子提交＋设备等待通道；潜在少一次回合，但先决条件是执行权限隔离。
- B：通知预送正文但保留claim＋设备等待通道；可保留既有防重复结构，收益须测；另提出分段回复。
- 评判采用B为基础，优先真实计时和设备交付；吸收A的原子回答作为有条件实验，拒绝默认取消claim，暂不采用B的分段回复。主协调者已读取完整候选和评判，并核对上述源码、官方接口及最新计时，接受此裁决。

当前结论是优化方案，不是性能改善结果。无法确认新方案能省多少秒，也没有证据支持稳定低于10秒。
